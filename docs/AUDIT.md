# V3 reliability and portability audit

Reviewed on 16 October 2026. Scope: static inspection of legacy `ail-typo-squatting V-3` at Git revision `eff48ca`, whose application, worker, and report writer are generated inside its installers. No installer, external scan, DNS enumeration, or screenshot capture was run. References below use that revision's source line numbers, not generated-file line numbers. The Python implementation and replacement Dockerfile are separate changes.

## Why the changelog is unreliable

The main problem is changing scan coverage, not Docker. V3 moves the previous results aside, discovers subdomains again, and generates candidates from only the current discovery output (`install.sh:69–100`). If yesterday's `login.example.com` is absent from today's passive discovery, all its generated candidates disappear from today's input. Their absence says nothing about their current DNS state.

[Subfinder describes itself as passive enumeration](https://github.com/projectdiscovery/subfinder). Its sources, API credentials, and time limits affect results. Its [documented flags](https://docs.projectdiscovery.io/opensource/subfinder/usage) include source selection, JSONL output, collected source names, and timeouts. Adding `-all` may increase coverage; it cannot establish that a missing name was deleted.

A trustworthy comparison needs persistent inventory plus explicit observations. Keep previously known seeds and candidates and recheck them directly. Record the difference between “not rediscovered”, “not checked”, “DNS lookup failed”, “NXDOMAIN”, and “NOERROR with no answer”. Keep the last successful observation through transient failures. Compare only compatible query types, resolver settings, generation configuration, and scope. A newly generated candidate is “newly monitored”; reserve “newly resolving” for a candidate with an earlier comparable negative observation.

## Confirmed legacy defects

All paths in this table are relative to the original `ail-typo-squatting V-3/`,
now preserved unchanged under `legacy/ail-typo-squatting V-3/`.

| Finding | Evidence and consequence |
| --- | --- |
| Wrong backup directory | `install.sh:52,71` writes `output/<company>/backups/<timestamp>/`. `installapp.sh:105–108` instead chooses the maximum immediate child of `output/<company>/` and looks for a report there. It may choose `screenshots`, `domains`, or `backups`; none has the expected report directly inside it. |
| Comparison uses worksheet positions | `installapp.sh:110–112` uses `DataFrame.isin(other_dataframe)` then `dropna()`. This is an elementwise comparison aligned by row/column labels, not a domain/record-key comparison. Reordered rows and unchanged cells can create or suppress differences. No removed-domain result is produced. |
| Broken comparison page and navigation | `installapp.sh:116` renders `compare_reports.html`, which the installer never creates. Dashboard report links at `installapp.sh:180–181` omit the required company parameter. |
| Partial failures look successful | The worker generated by `install.sh:24–131` checks no stage return values and ends by printing success. A failed discovery, generator, DNS query, or report can therefore leave an incomplete report and an apparent successful run. Previous output was already moved away. |
| DNS resolution is called registration | `install.sh:112–118` invokes MassDNS with its default A query and keeps A answers for screenshots. No registration lookup exists. IPv6-only and mail-only names are outside that check; a registered name need not publish A records. CNAME answer owners can also differ from the original candidate, so keep query identity separately. |
| Screenshot report is not a data store | `install.sh:249–265` embeds images in XLSX drawings. `installapp.sh:93–95` later reads worksheet cells with pandas and assumes those cells contain image URLs. Embedded drawings do not supply those URLs. Persist screenshot paths/metadata separately and generate XLSX as an export. |
| Queue has races and executes text | Locks use separate existence checks and `touch` (`install.sh:35–43,142–148`), allowing concurrent workers. The queue is world writable (`:32`) and its text is executed using `bash -c` (`:156`). Use transactional job claims and structured arguments. |
| Unsafe web execution and file paths | `installapp.sh:57–67` puts form fields into a shell command with `shell=True`; metacharacters are executed and spaces break arguments. Company and download paths are not confined to the output root (`:62,122–127`). The app also exposes a crontab editor and starts Flask debug mode on all interfaces (`:72–87,145`). |
| Inconsistent configuration names | Docker copies `domainlists/` and `my-crontab`; the app uses `domain_lists/` and reads `my-crontab.txt` (`Dockerfile:12,15`; `installapp.sh:29,79,85`). The crontab page fails on a fresh installation until that differently named file exists. |
| Builds are not reproducible | Rolling Kali, `apt upgrade`, unpinned packages, an unpinned upstream Git clone, and global pip installs change tool versions between builds (`Dockerfile:2`; `install.sh:1–2,286–289`). The container command keeps `tail` alive even if the app dies (`Dockerfile:33`). |

## Linux server and container direction

The intended host is a Linux server, with Docker providing an isolated test environment and a deployment option. That is a reasonable fit. Keep Docker while replacing installer-generated application code with checked-in Python modules. Python should own persistence, comparison, jobs, reports, and the web interface; specialist tools can remain executables. Native Windows compatibility is optional rather than a migration requirement.

| Component | Upstream evidence | Recommendation |
| --- | --- | --- |
| Subfinder | Its [release build configuration](https://github.com/projectdiscovery/subfinder/blob/dev/.goreleaser.yml) includes Windows, Linux, and macOS. | Include a pinned executable in the Linux image; use argument lists, capture exit status/stderr, save JSONL and source provenance, and record the installed version. |
| MassDNS | Its [README](https://github.com/blechschmidt/massdns) documents non-Linux builds and Windows through Cygwin. It defaults to A and offers NDJSON with terminal failures (`-o Je`). | Start with a Python DNS backend and bounded concurrency. MassDNS remains a possible bulk adapter if measured workload size justifies it; preserve query identity and explicit failure results. |
| gowitness | Its [README](https://github.com/sensepost/gowitness) supports Linux/macOS and describes Windows support as mostly working. Chrome is required. The [file command source](https://github.com/sensepost/gowitness/blob/master/cmd/scan_file.go) says metadata needs explicit `--write-*` flags. | Keep capture independent of DNS success and read metadata rather than infer filenames. The replacement image now includes pinned Gowitness 3.2.2 and Chromium; native setups supply these binaries separately. See [capture integration](SCREENSHOTS.md). |
| AIL typo generator | The [upstream README](https://github.com/typosquatter/ail-typo-squatting) documents a pip-installable Python library, specific algorithms, and `runAll`. | Include `ail-typo-squatting==2.7.6` to preserve algorithm coverage. Persist generator version/settings and freeze existing candidate sets. A small replacement generator is not equivalent to all upstream algorithms. |
| cron/Bash/Kali | These dependencies come from the legacy orchestration and installers, rather than the comparison problem. | Replace orchestration with Python and a persistent job queue. Use a normal slim Python image and one production WSGI application process. Add scheduling against the same job interface later. |

The replacement Dockerfile uses `python:3.12-slim-bookworm`, runs as UID/GID 10001, and stores application state under `/data`. Compose supplies a named volume, init process, restart policy, read-only application filesystem, temporary `/tmp`, and a loopback-only port mapping for testing or a local reverse proxy. The image healthcheck calls `/health` using Python; it does not invoke a scanner. A single foreground application process makes exit and restart behavior observable.

Subfinder is built separately at [release v2.17.0](https://github.com/projectdiscovery/subfinder/releases/tag/v2.17.0), published 8 October 2026. That tag's [go.mod](https://github.com/projectdiscovery/subfinder/blob/v2.17.0/go.mod) requires Go 1.26; the builder uses `golang:1.26.9-bookworm`, listed in the [official image manifest](https://github.com/docker-library/official-images/blob/master/library/golang). This avoids the old rolling Kali installation. Base-image tags and transitive pip dependencies still need a maintenance/update policy; these changes do not constitute a fully locked dependency supply chain.

Recommended storage is SQLite with projects, configured roots, retained discovered seeds, candidate provenance, runs, per-name/per-record observations, screenshots, and stage errors. Give each run a unique ID and immutable raw artifacts. A database transaction should publish a completed comparison only after required stages succeed. Optional capture failure should be visible without invalidating otherwise complete DNS evidence. A local web UI should display coverage and failures beside changes and run long jobs outside the HTTP request.

Import legacy inventories as historical evidence with unknown coverage. Existing XLSX files can establish that an answer was observed; their omissions cannot establish a negative observation. Validate the new workflow with fixtures covering fluctuating discovery, reordered records, timeouts, NXDOMAIN, NODATA, AAAA-only names, changed settings, failed stages, and interrupted runs before comparing live results.
